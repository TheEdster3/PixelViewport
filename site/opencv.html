INTEGRATION GUIDE / 01 · WINDOWS ALPHA

From OpenCvSharp Mat
to an Avalonia viewport.

Keep OpenCV responsible for processing. Give the viewport a frame with a clear lifetime. The important decision is not a widget property: it is who owns the pixels after submission.

1. Run the existing proof first

Install the .NET 8 SDK on Windows. Clone the public repository and run the Avalonia sample:

git clone https://github.com/TheEdster3/PixelViewport.git
cd PixelViewport
dotnet run --project samples/PixelViewport.VisionDemo -c Release

This sample uses synthetic managed BGRA32 frames. It lets you verify zoom, pan, frame presentation, and inspection before connecting an acquisition source.

2. Add the optional adapter

Reference PixelViewport.Avalonia and PixelViewport.OpenCvSharp using project references or packages from the GitHub alpha release. Public NuGet availability is tracked in the repository; do not assume a package has been published there.

The adapter pins OpenCvSharp 4.11.0.20250507 for the supported .NET 8 toolchain. It does not include native OpenCV binaries. Your Windows application must supply a matching native runtime, such as the version used by the repository's OpenCvSharp integration tests. Review dependency and redistribution notes.

3. Choose one ownership model

Transfer a Mat you no longer need

using OpenCvSharp;
using PixelViewport.OpenCvSharp;

// viewport is a PixelViewport.Avalonia.ImageViewport.
Mat processed = AcquireOrProcessFrame();
viewport.SubmitFrame(MatFrameAdapter.TakeOwnership(processed));

// Do not dispose, mutate, or reuse processed after submission.
// PixelViewport disposes it when that frame is released.

AcquireOrProcessFrame() stands for your application's existing acquisition or processing code; it is not a PixelViewport API. Do not put an ownership-transferred Mat inside a producer-side using block.

Copy a Mat that your pipeline retains

using Mat processed = AcquireOrProcessFrame();
viewport.SubmitFrame(MatFrameAdapter.Copy(processed));

// The viewport owns its copy; the caller retains processed.

Copying also packs non-contiguous Mat ROIs safely row by row. Ownership transfer preserves the original step/stride and retains the Mat itself; it does not make the downstream renderer zero-copy.

4. Match the supported formats

  • CV_8UC1 → Gray8
  • CV_16UC1 → little-endian Gray16
  • CV_8UC3 → BGR24
  • CV_8UC4 → BGRA32

These are image-format contracts, not a promise to accept arbitrary Mat element types. Float images, packed 10/12-bit camera data, and Bayer mosaics need conversion in your own pipeline first.

5. Plan for rendering to fall behind

Submission can originate on a producer thread. The mailbox keeps only the newest pending frame, releasing replaced frames rather than building a backlog. Keep your acquisition and image processing off the UI thread; the current Avalonia alpha still converts the selected frame on the UI thread.

Inspect viewport.FrameStatistics and the FramePresented event. A dropped pending frame is an intentional freshness policy, not a silently lost acquisition record. Store acquisition data elsewhere if every frame must be retained.

No sustained FPS, GPU, or end-to-end latency claim is implied by ownership transfer. Measure the actual image format, size, workload, and target hardware. Linux has not been validated.

Next: verify with your data

Start with a non-confidential format, dimensions, stride, target rate, and overlay count. Agree on measurement boundaries before comparing alternatives.
